## Findings

### HIGH - Verification boundary failure

Earlier work treated compilation, code review, and partial flash/readback
evidence as if they closed hardware/product behavior. That was wrong. Physical
panel parity, raw touch contact, Wi-Fi/pool/mining runtime, accepted-share
signals, dashboard/API behavior, and restore round-trip remain unproven for the
custom fork.

Impact: old "complete" language made the project look farther along than the
evidence supports.

Remediation: keep the fork artifacts as recovery context and require actual
runtime evidence before any live-device claims.

### HIGH - Route drift in `07-01`

`07-01-PLAN.md` contained a correct active-route override but still had
machine-readable plan fields and a main objective for flashing the fork.

Impact: future GSD resumes could follow the wrong route despite the override.

Remediation performed: `07-01-PLAN.md` now records BIN-01..BIN-05 in
frontmatter, objective, active tasks, threat model, verification, success
criteria, and output. The old fork flash tasks are parked under a legacy recovery
appendix.

### HIGH - Progress counter ahead of actual goal

The GSD progress counter reports `96%` because 22 of 23 plan artifacts are
counted complete. That is not the same as completing the binary customization
goal or recovering the live device.

Impact: status can be misread as "almost done" when the remaining work contains
the highest-risk proof gates.

Remediation: authority docs now explicitly state that `96%` is an artifact
counter, not product completion.

### MEDIUM - Firmware identity drift

The current live custom fork intentionally reports `v2.0.02`, so version text
alone cannot identify stock firmware. The official baseline is the backed-up
and locally verified `v2.0.02` ST7789 app. The June 1 factory dump is
historical `v1.8.28`.

Impact: visual/API version strings can mislead future work into thinking the
stock binary is live.

Remediation: authority docs now route identity checks through provenance and
hash/offset evidence, not version text.

### MEDIUM - Forensic and authority staleness

The prior latest forensic report predated the final route correction and still
framed Phase 7 primarily as on-device validation.

Impact: resume readers could over-prioritize fork recovery and touch/UI work.

Remediation performed: this report is the current forensic record, and
`07-AUTHORITY-INDEX.md` points here as latest.

### MEDIUM - Dirty worktree risk

The repo contains a large dirty worktree with prior-session edits, untracked GSD
artifacts, and generated local files. This is expected in the recovery context,
but it increases interruption and accidental-revert risk.

Impact: broad cleanup or reset commands could destroy evidence.

Remediation: do not use destructive git commands. Keep edits narrow and review
status before any commit or archive step.
